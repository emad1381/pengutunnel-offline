# نتیجهٔ نسخهٔ مستقل از سرویس لایسنس

فایل نهایی این مرحله `pengutunnel.offline.elf` است. این فایل با نسخهٔ قبلی `pengutunnel.signature-diagnostic.elf` تفاوت دارد: در مسیرهای آزموده‌شده به سرور لایسنس، پاسخ ساختگی، کلید لایسنس یا گواهی آزمایشی احتیاج ندارد. هر دو طرف باید از همین نسخه استفاده کنند.

## تغییر انجام‌شده

کپی نهایی از باینری اصلی v5.1.3 ساخته شده و سه تغییر محدود دارد:

1. مسیر بررسی لایسنس، بدون درخواست HTTP و بدون token، نتیجهٔ بدون خطا برمی‌گرداند.
2. مرحلهٔ پرسیدن IP از طرف مقابل که پیش‌نیاز انتخاب IP لایسنس در reverse L4 بود، اجرا نمی‌شود.
3. راه‌اندازی کنترلر origin و worker پس‌زمینهٔ آن انجام نمی‌شود.

چیدمان ELF، کد PSK، رمزنگاری transport و پیاده‌سازی Ed25519/TLS تغییر نکرده‌اند. تغییرها و بایت‌های قبل/بعد در `offline-build-final.json` ثبت‌اند و `build_offline.py` از روی هش مشخصِ نسخهٔ اصلی این کپی را بازتولید می‌کند. این patch برای باینری دیگری مناسب فرض نشده است.

SHA-256 فایل نهایی:

```text
5d58cdde3483029a70c8b52b9434c4fe4bb4fbc093e47c5c38aba4be9361fb52
```

کد اصلی لایسنس از تمام نقاط باینری پاک نشده است؛ ورودی‌های مشخص‌شدهٔ آن در مسیر تونل کنار گذاشته شده‌اند. در نتیجه بعضی پیام‌های قدیمی مانند `license is valid` یا عبارت license در لاگ هنوز چاپ می‌شوند. این پیام‌ها در نسخهٔ آفلاین به معنی دریافت تأیید از ناشر نیستند.

## شواهد آزمایش

در هر آزمایش، server و client در namespace جدا با شبکهٔ loopback و chroot اجرا شدند. هیچ سرویس لایسنس ساختگی راه‌اندازی نشد، پورت‌های 2053 و 2096 بسته بودند، هیچ CA آزمایشی به process داده نشد و بخش `[license]` از تنظیمات client حذف شد. تنها سرویس echo و خود دو طرف تونل فعال بودند.

| آزمون | نتیجه |
|---|---|
| reverse tcpfwd، tls، ws، wss، xhttp و xhttps با AES-GCM | هر شش حالت موفق |
| دادهٔ ۶۴ بایت، ۶۴ KiB و ۱ MiB | در هر شش حالت عیناً برگشت؛ هش داده‌ها برابر بود |
| health دو طرف | HTTP 200، `alive:true` و یک peer |
| tcpfwd با ChaCha20-Poly1305 | موفق برای هر سه اندازه |
| direct tcpfwd و direct TLS | موفق برای هر سه اندازه |
| PSK متفاوت در دو طرف | اتصال رد شد؛ انتقال موفقی صورت نگرفت |

شواهد آزمون‌های اصلی `offline-v3-*.json` و آزمون‌های تکمیلی `offline-extra-*.json` هستند. خلاصه در `offline-test-summary.json` قرار دارد. خروج ۱ client در بعضی پایان‌ها ناشی از پیام restart هنگام بستن کنترل‌شدهٔ server است و همراه با موفقیت انتقال و health ثبت شده؛ نباید آن را شکست راه‌اندازی تلقی کرد.

این آزمون‌ها کوتاه و محلی‌اند. استقرار روی دو سرور واقعی، اجرای بیش از یک ساعت، بار طولانی، TUN، raw IP، CDN، source spoof و ban sync در این مرحله تأیید نشده‌اند. راه‌انداز کنترلر origin از روی کد کنار گذاشته شده، اما آزمون زمان واقعیِ یک‌ساعته انجام نشده است.

## نصاب همراه

`install-offline.sh` از متن بازشدهٔ نصاب اصلی مشتق شده است:

- فقط فایل `pengutunnel.offline.elf` کنار خودش را پس از کنترل SHA-256 نصب می‌کند.
- کلید لایسنس نمی‌پرسد و برای کانفیگ جدید بخش لایسنس نمی‌سازد.
- دریافت خودکار core و script از upstream را انجام نمی‌دهد.
- هنگام اجرای نصاب، timer/service به‌روزرسانی خودکار core را غیرفعال می‌کند تا باینری upstream جایگزین نسخهٔ آفلاین نشود.
- keeper موجود را در راه‌اندازی معمول غیرفعال نمی‌کند؛ پاک‌سازی keeper هنگام حذف کامل همچنان وجود دارد.
- ابزارهای اختیاری مانند انتخاب DNS/mirror یا IP probe از منوی اصلی باقی مانده‌اند؛ انتخاب آن‌ها می‌تواند تماس شبکه‌ای مستقل از لایسنس ایجاد کند.

نصاب با `bash -n` کنترل نحوی شده است. اجرای کامل آن با root روی سرور واقعی در این مرحله انجام نشده است. هسته در sandbox واقعاً اجرا و آزمایش شده است.

## اجرا از بسته

فایل zip را روی هر دو سرور Linux x86-64 باز کنید و دو فایل نصاب و هسته را کنار هم نگه دارید:

```bash
chmod +x pengutunnel.offline.elf
sudo bash install-offline.sh
```

برای هر دو سمت یک PSK قوی و یکسان انتخاب کنید. PSK با کلید لایسنس متفاوت است و همچنان لازم است. فایل‌های نمونه از نشانی و PSK جایگزین‌شدنی استفاده می‌کنند. آدرس peer و پورت‌ها را متناسب با دو سرور خود تنظیم کنید.

این فایل، سورس بازسازی‌شده یا محصول اصلیِ بازکامپایل‌شده نیست؛ کپی اصلاح‌شدهٔ یک build مشخص است. برای شرح ساختار و حدود پوشش به `ARCHITECTURE.fa.md` و `CONFIG-STRUCTURE.fa.md` مراجعه کنید.
