# تطبیق مستقل نصاب با نسخهٔ اصلی

## ورودی و دامنه

- اصل بازشده: `install.decoded.sh.txt`، نسخهٔ 4.2.6.
- نسخهٔ موجود مخزن: `../pengutunnel-offline/install-offline.sh`.
- پیشنهاد اصلاح‌شده: `install-parity.sh`؛ هسته و فایل‌های مخزن در این بررسی تغییر نکردند.
- SHA-256 پیشنهاد: `896853291178f9d6f68d9f45ba81825da4093762959f8ddcf3be88a659b9b950`.

این بررسی مقایسهٔ متن Bash و آزمون محدود منطق ورودی بود؛ بررسی باینری با REA، نصب root روی سرور و اثبات رفتار شبکه نیست.

## تطبیق قابلیت‌ها

شماره‌ها و مسیرهای منوی اصلی 0 تا 11 حفظ شده‌اند: تنظیم تونل، مدیریت، وضعیت، x-ui ban sync، به‌روزرسانی خودکار، نصب مجدد core، نصاب، حذف، mirror، DNS و IP probe. گزینه‌های update حفظ شده‌اند ولی رفتار آن‌ها عمداً با اصل فرق دارد: core فقط از فایل محلی با hash مشخص نصب می‌شود و update راه دور فعال نمی‌شود.

در مقایسهٔ بلوک‌های متن تابع، از 31 تابع انتخاب‌شدهٔ `cn_*`، `l4_*`، `configure_new` و `gen_psk`، تعداد 29 بلوک عیناً با اصل یکسان‌اند. استثناها `cn_license` برای حذف پرسش لایسنس و `cn_side` برای قطع امن EOF هستند. این مقایسهٔ متن است و اثبات برابری رفتاری همهٔ مسیرها نیست.

- انتخاب TUN / no-TUN / DNS / SSH / TLS و پروتکل‌های خام، تنظیم pool، cipher، health، PSK و forward حفظ شده است.
- helperهای انتخاب CDN و source-IP/SNI spoof حفظ شده‌اند. بخش تولید تنظیمات `spoof_source`، `spoof_peer`، `sni_spoof`، نام، TTL و strict در اسکریپت وجود دارد.
- در wizard لایهٔ ۴ تنها بلوک درخواست و تولید license حذف شده و EOF مهار شده است؛ انتخاب transport و مسیرهای direct/reverse باقی‌اند.
- PSK حذف نشده؛ مرحلهٔ دریافت PSK و تولید خودکار آن حفظ شده است.
- `cn_license` مقدار `lic_enabled=false` و کلید خالی می‌دهد؛ writer اصلی `[license]` در مسیر غیر-L4 هنوز تحت شرط غیرقابل‌دستیابی از wizard معمول باقی است. در L4 `lic_block` خالی است. کانفیگ‌های قبلی در این تغییر خودکار پاک‌سازی نمی‌شوند.
- نمایش sysinfo با اصل یکسان نیست: IP از route محلی گرفته می‌شود، نه lookupهای عمومی و سرویس upstream؛ location برابر local است. IP محلی پشت NAT لزوماً IP عمومی سرور نیست.

## یافتهٔ اجرایی و اصلاح

### پیش‌نیازهای سیستم در نسخهٔ قبلی ممکن بود نصب نشوند

در اصل، `ensure_core` پیش از نصب اولیه `install_prereqs` را صدا می‌زد. نسخهٔ آفلاین موجود این فراخوانی را حذف کرده بود. چون همان startup فایل BIN را نصب می‌کرد، مسیرهای بعدی wizard هم با دیدن BIN موجود، نصب پیش‌نیازها را رد می‌کردند. بنابراین روی سرور پاک، ابزارهایی مانند `ip` و `curl` ممکن بود موجود نباشند.

در پیشنهاد، `ensure_core` ابتدا `install_prereqs` را اجرا می‌کند و در صورت خطا نصب را متوقف می‌کند؛ این بررسی حتی وقتی core نصب‌شده hash درست دارد انجام می‌شود. نصب package سیستم ممکن است به مخزن سیستم‌عامل نیاز داشته باشد؛ این نسخه به معنای صفر بودن وابستگی‌های OS نیست.

### پایان ورودی می‌توانست منو یا wizard را در حلقه نگه دارد

در اصل و نسخهٔ قبلی، `read` ناموفق نادیده گرفته می‌شد. `ask_req` و `ask_yn` می‌توانستند بی‌پایان تکرار شوند؛ منوی اصلی نیز خروجی خالی ask را دوباره درخواست می‌کرد. wizard مرحلهٔ اول با EOF مشابه «بازگشت» رفتار می‌کرد و می‌چرخید.

در پیشنهاد، خانوادهٔ ask شکست read را برمی‌گرداند؛ منوهای حلقه‌ای این شکست را بررسی می‌کنند. wizardها EOF را در `INPUT_EOF` ثبت می‌کنند و کنترل‌کننده و مسیر L4 متوقف می‌شوند. شروع کامل نصاب هم terminal تعاملی می‌خواهد. ورودی معتبر، defaults و شماره‌های منو حفظ شده‌اند. این اصلاح ادعای audit کامل همهٔ مسیرهای input و عملیات تخریبی نیست.

## Keeper و update: مرز برابری با اصل

در نسخهٔ قبلی، keeper فقط به auto-update وابسته بود و روی نصب تازه فعال نمی‌شد. در پیشنهاد نهایی، شمارهٔ 5 حفظ و برچسب آن به `Auto-update / keeper` تغییر کرده است. submenu گزینه‌های enable، disable، status و back برای keeper محلی دارد. به‌روزرسانی راه دور همیشه غیرفعال است و enable keeper هیچ دانلودی انجام نمی‌دهد.

`kp_enabled` و `kp_disable` مستقل‌اند؛ خاموش‌کردن keeper timer و service خودش را متوقف می‌کند و به updater دست نمی‌زند. حذف کامل (`au_disable`) هر دو گروه را جمع می‌کند. `kp_install` متن محلی keeper و unitهایش را می‌نویسد و timer یک‌دقیقه‌ای را فعال می‌کند. در متن keeper جدید، `license_stop`، خواندن journal/log برای خطای لایسنس و lock مربوط به updater حذف شده‌اند. keeper فقط واحدهای enabled با وضعیت غیر active/activating/reloading/deactivating را دوباره start می‌کند و lock و log محلی دارد. این بازیابی شامل واحد failed هم می‌شود؛ رفع علت خطا را تضمین نمی‌کند.

startup ابتدا پیش‌نیاز و core را بررسی می‌کند و سپس `load_sysinfo` را اجرا می‌کند تا `ip` نصب‌شده در دسترس باشد. بلوک مردهٔ `au_enabled && ...` از startup حذف شده است. برای بازنویسی keeper نصب‌شدهٔ قدیمی، گزینهٔ enable keeper را اجرا کنید. خاموش‌کردن timer/service شناخته‌شده ثابت نمی‌کند هیچ cron یا updater بیرونی روی یک سرور موجود نیست.

## آزمون‌های انجام‌شده

- `bash -n` پیشنهاد موفق بود.
- آزمون تابعی EOF برای `ask`، `ask_req`، `ask_yn`، `wask`، `wask_req` و `wyn` موفق بود.
- منوی اصلی با EOF خارج شد و با گزینهٔ 0 خروج موفق داشت.
- EOF در مرحلهٔ اول، کنترل‌کنندهٔ wizard و wizard لایهٔ ۴ به‌جای حلقه متوقف شد.
- با mock، فراخوانی پیش‌نیازها برای core موجود و توقف روی خطای پیش‌نیازها بررسی شد.
- خاموش‌ماندن مرحلهٔ لایسنس و دریافت همان PSK ورودی بررسی شد.

- با mock فایل اجرایی `systemctl` و مسیرهای موقت، تولید keeper و unitها، enable/status/disable/back، خروج EOF، اجرای متن keeper و start شدن فقط دو واحد enabledِ failed/inactive بررسی شد. واحدهای active، activating، deactivating و disabled start نشدند؛ هیچ فراخوانی updater در این آزمایش ثبت نشد.

آزمون‌ها در WSL روی بخش تعریف توابع (پیش از entrypoint `need_root`) اجرا شدند. `banner` و بررسی نسخه/core در مسیر آزمایشی mock شدند؛ هیچ core، سرویس systemd، نصب package یا اتصال شبکه‌ای در این آزمون‌ها اجرا نشد. fixture اولیهٔ آزمون core موجود اشتباهاً `/dev/null` را فایل regular فرض کرده بود و اصلاح شد؛ آزمون نهایی با فایل regular موفق بود.

## برای ادغام

آزمون‌ها به صورت harness قابل اجرای دوباره در `check-parity-installer.py` ذخیره شدند. اجرای نهایی آن روی پیشنهاد، 20 بررسی موفق به‌اضافهٔ syntax هر دو manager/keeper و ترتیب startup داشت:

```bash
python3 check-parity-installer.py /absolute/path/to/install-parity.sh
```

harness بخش تعریف توابع را پیش از entrypoint مستقل `need_root` استخراج می‌کند، از `systemctl` ساختگی و مسیرهای موقت استفاده می‌کند و backendهای شبکه و نصب بسته را در PATH مسدود می‌کند. فایل ورودی باید مورد اعتماد باشد: این harness sandbox برای Bash ناشناخته نیست. هیچ entrypoint روت، systemctl واقعی، نصب package، network backend یا ELF هدف در اجرای نهایی اجرا نشد.

در صورت جایگزینی manager مخزن با این پیشنهاد، مقدار `MANAGER_SHA` در bootstrap `install.sh` باید با SHA بالا عوض شود و بسته/manifest قبلی نیز دیگر نمایندهٔ این manager نیست. هستهٔ ELF و hash آن در این تغییر ثابت است.

وجود و حفظ گزینه‌های spoof یا config به معنای تأیید عملکرد spoof نیست. ارتباط دو سرور واقعی ایران/خارج، TUN/raw IP، CDN، چندساعته، ban sync و نصب کامل root همچنان به آزمون واقعی جداگانه نیاز دارند. عبارت «دقیقاً یکسان در همهٔ رفتارها» با شواهد این بررسی قابل تأیید نیست.
